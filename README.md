# VECTOR CRM

## Telegram channel

The car's Telegram tab targets only the user-specified **@boom_avto_vrn**. It stores drafts in `car.telegram` and durable connection/preview/outbox records under `telegram:*` in existing `app_meta`; no schema change. Configure `TELEGRAM_BOT_TOKEN` as a Sites secret, apply the runtime configuration with deployment, add that bot to the channel as an administrator with posting rights, then use the owner-only connection check. The check calls getMe/getChat/getChatMember and sends no messages. Numeric channel ID is pinned after checking; channel reassignment or a different bot blocks updates. Tokens are never returned to the browser, logged, or stored in car records; connection metadata contains a one-way fingerprint only.

Owners can preview and explicitly confirm a post or text update. Editors can save drafts; viewers cannot write. A reviewed preview is bound to car revision, owner, operation and ten-minute lifetime. Only selected car JPG/PNG photos (1–10, 10 MB each, 25 MB total) are uploaded directly through multipart; no public CRM file URLs are required. A photo/album with a short model caption is followed by a separate message up to 4096 characters. Price/specifications come from current card fields, and contact is explicitly entered for publication. Passport/party/payment documents, VIN, costs and private notes are excluded. WEBP and video posting are not in this first Telegram implementation.

Stored message IDs support explicit text/price updates and a sold marker without reposting the album. No automatic posting on save, no bulk send or schedule, no Telegram deletion. Published photo selection is fixed; text edits remain possible after original CRM photos are deleted. The existing VECTOR AI stays read-only. The optional description helper reuses Avito's allowlisted AI proposal function and quota; applying its suggestion changes only the draft form.

A durable compare-and-swap outbox prevents concurrent/duplicate sends. Telegram-confirmed 4xx failures before sending any message allow a new preview/retry. Network uncertainty, interrupted jobs or partial delivery block new publication for that car and instruct the owner to inspect the channel and manually finish any missing text. **Do not blindly reset these outbox records**: Telegram's send API does not provide a client idempotency key or a message-read reconciliation API. Uncertain edits can be retried against the same message ID. Outbox state is authoritative; car history is best-effort after a confirmed send and does not convert an audit conflict into a duplicate send.

`tests/telegram.test.mjs` uses the actual worker/SQLite flow and mock Telegram responses to check safe projection, connection permission checks, concurrency, stale previews, role/CSRF checks, single-photo/album paths, linked price, sold text, definite/uncertain/partial failures and token-safe errors. No real Telegram messages or paid AI calls were made during development. Real bot credentials, channel permission verification and a user-approved trial post are still needed. Source: https://core.telegram.org/bots/api.

## Avito preparation module

The car's «Авито» tab stores an incomplete draft independently of export readiness in the existing car JSON. No schema change or automatic migration of customer records. VIN/year/mileage/color/sale price remain linked to the core card; Avito-specific catalog names, IDs, text, contacts and photo selections are saved with the car revision and audit event. Editing the core sale price is reflected in later exports. Only brand/model remain required for normal car creation.

Export follows the user's original **used-cars Excel template dated 10 September 2026**. The blank source workbook is in `public/templates`; its instructions, first four rows and dictionaries are preserved. Preparation returns XLSX plus a flat ZIP of explicitly selected car photos. WEBP is converted to JPEG in the browser only for export. No passport, party, contract, payment document, internal expense or private note is exported; photos use existing authenticated file routes. Each image is at most 25 MB and the full export is at most 100 MB. Current browser preparation is limited to 50 cars. Final revision verification rejects changes during preparation. A partial uploaded file may remove other Avito listings: the UI warns to reconcile the complete inventory before uploading.

The original template has no populated make/model/generation/modification catalog. Required `GenerationId`/`ModificationId` must be obtained and checked against Avito, not inferred. The module validates template fields and enum values but cannot establish live catalog validity or guarantee Avito acceptance/moderation. There is no separate exported `Title` field in this category. A hand-entered «Опубликовано» status needs an Avito link or ID and is explicitly not platform confirmation. «Продано» removes selection in the form; save to persist.

This is **manual export preparation, not automatic posting**. Avito's feed schedule/API is not connected; marking a car never publishes or unpublishes it. The existing Boom Auto control retains its existing owner-only workflow. Telegram/Instagram controls are visibly disabled and labeled unconnected. No external account credentials or new public endpoints are added.

Dedicated ad AI returns a reviewed proposal, never writes cars. It reuses the configured OpenAI key/model; only allowlisted non-personal car characteristics are sent, with `store:false` (not a zero-retention guarantee). The market button requires real web-search source URLs on Avito/Auto.ru/Drom and at least three matching full-price offers before computing a sample average/median. It is a small asking-price sample, not an appraisal or full-market statistic. Rate limits: 50 text / 10 market requests per user/day, not a monetary cap. Provider responses, availability and model quality need a user trial; automated tests mock OpenAI and never incur charges. The general VECTOR AI remains read-only and can search the new tab.

`tests/avito.test.mjs` checks the actual worker/SQLite flow, incomplete drafts, linked price, revision conflicts, safe export projection, exact template preservation/formula safety, AI proposal-only behavior, source filtering, roles and CSRF. No real cars are altered by tests and no ad is sent to Avito.

## VECTOR AI

The inventory page contains an authenticated, per-user AI conversation for owners/editors. `OPENAI_API_KEY` is reused from passport recognition; optional `OPENAI_ASSISTANT_MODEL` and `OPENAI_TRANSCRIPTION_MODEL` override defaults documented in `.env.example`. Uses OpenAI Responses structured output with `store:false`; audio transcription returns editable text, never executes commands.

VECTOR AI is now **read-only**. The assistant cannot change cars, prices, people, costs, routes, descriptions, attachments or publication. Manual CRM editing is unchanged. The legacy execution/cancellation endpoints always reject with 403, including previously saved proposals; old mutation modules are removed from the application.

Every question reads fresh car records. Sources cover overview, full route milestones/dates, calculated route durations, cost basis and extra expenses, document/payment/party fields and file metadata, photo/video metadata, history and publication text. Responses link directly to the relevant car tab. Saved PDF/photo/Word bytes are not read; passport fields are supplied only for relevant questions. Source context is capped at 160,000 JSON characters with an explicit omission count, history at 100 entries (10 for non-history questions).

Basic arrival/purchase/departure dates, route lists, durations, sale price and total costs are answered deterministically from database fields without a paid AI call. Ambiguous matches offer explicit vehicle choices. Complex questions use Responses structured output; source IDs are validated against the supplied context, and stored CRM strings are treated as untrusted data. Last 20 messages persist separately from old proposals in D1 app_meta `assistant:read-thread:<user hash>`. Only chat state/counters are written. Voice is up to 60 seconds; transcription returns editable text, not an executed command. Limits are 100 AI questions and 100 transcriptions per user/day, not a monetary budget. Direct database answers do not use the AI question quota.

`tests/assistant-readonly.test.mjs` covers actual worker/database retrieval, old execution endpoint rejection, no vehicle/file mutations, ambiguous identities, fresh route changes, missing dates, source completeness, grounded source IDs and role isolation. OpenAI is mocked only for complex-answer/transcription protocol tests; this does not establish general model answer quality. No real customer records or paid AI calls are used. Browser microphone support and provider model/billing access require a user-side trial.

## Runtime

React + Vite client; a Cloudflare Worker with managed D1 database `DB`. Private audience is enforced by Sites before serving the application, API, or attachments. No auth tokens are shipped to the client or committed. Photos/documents up to 10 MiB and videos up to 20 MiB are stored as base64 chunks in D1; metadata and chunk writes are atomic. Cars use optimistic revisions with unique write IDs to prevent stale overwrites. Amounts are rounded to kopeks at the cost-entry level. Stock days stop on soldDate.

## Development

Use the Node version installed in the primary runtime. `npm ci`, `npm run build`, `npm run dev` (local worker, port 4173). This project was initialized from the available offline package cache. `node --test tests/*.test.mjs` runs real application handlers with a SQLite implementation of the D1 interface. `scripts/check-live.py` runs an authenticated integration check against the private deployment using the `VECTOR_TEST_TOKEN` environment variable; never save that value in a file.

## Publish

Build with `npm run build`. Commit and push the exact source to the Sites-provided private repository; read the full HEAD SHA after a successful push. Package with `node scripts/package.mjs /absolute/path/vector-crm-build.tgz`. Save that archive and commit as a Site version, then deploy with the owner-private operation. The manifest deliberately has no `static` property so the packaged `dist/server/index.js` handles API requests; Sites provides static assets from `dist/client`. Keep the current owner-only audience unchanged.

## Product boundaries

The six clearly marked demo vehicles are synthetic. Their illustrations are placeholders, replaced by the first uploaded photo. Demo deletion removes demo cards and attached files, including edits made to demo cards, after an in-app confirmation. User-created vehicles can be archived and restored. JSON export contains records, costs, routes and audit history; file bytes are downloaded separately. No Drive/Supabase/GitHub account data is imported. Bank payments, automated exchange rates and contract generation are not included. Seller passport recognition is described below.

## Passport recognition

The seller form offers OpenAI vision and the existing on-device Tesseract fallback. `GET /api/passport/config` exposes only availability. `POST /api/passport/recognize` accepts up to three JPG/PNG/WEBP images (10 MiB total) and returns proposed fields without writing to the database. Sites owner-only authentication protects both routes. The OpenAI request uses the Responses API, original image detail, a strict JSON schema and `store:false`; this flag does not imply zero provider retention. The UI explains that AI recognition sends images to OpenAI. Originals are attached only when the seller is explicitly saved.

Configure `OPENAI_API_KEY` as a **secret** through Sites runtime environment management, then deploy the saved version to apply it. Optional `OPENAI_PASSPORT_MODEL` defaults to `gpt-5.4-mini`; alternatives must support Responses, original image detail, low reasoning effort and structured outputs. Never put keys in client variables, source, logs or Git. Missing credentials leave the AI button disabled and the existing local/manual flow available. The selected model has not yet passed a real-image quality evaluation: activation is blocked on an account API key. Test against manually verified real documents after connecting; mocked API tests establish application behavior only, not OCR accuracy. Do not add passport photos or real personal data to the repository.

Unreadable or uncertain values remain blank; conflicting existing values require review. Multiple people in a single request suppress all proposed fields. Numeric formats and dates are checked before filling. No automatic retry incurs additional API charges.

References: https://developers.openai.com/api/docs/guides/images-vision and https://developers.openai.com/api/docs/guides/structured-outputs.

## Бум Авто publication

`src/publication.js` is the sole export projection. Each real, unsold, unarchived car has optional `publication` settings: explicit selected photo IDs and a separately authored public description. Publishing requires a positive sale price and at least one selected actual vehicle photo. Internal notes are never reused as the description. Seller/buyer documents cannot be selected by the API. Vehicle edits preserve publication settings.

The owner saves per-car settings, then clicks «Выгрузить каталог на сайт» to sync all eligible cars to https://boom-auto.divine-lime-4457.chatgpt.site. This is explicit manual snapshot synchronization; changes, sales, archival and photo deletions require another sync. A same-account tab acts as the transport using exact-origin/source/session postMessage checks; both apps keep Sites authentication. The Worker signs only the public projection and image hashes with `BOOM_SYNC_SECRET` (same secret on Boom, configured via Sites runtime tools, never source). The secret remains server-side. A final revision/fingerprint check rejects CRM changes during transfer. Empty selection clears the site's catalogue after explicit sync. No vehicles are selected automatically, including demo records.

No migration: publication settings are stored in the existing cars JSON; original storage, optimistic writes and audit trail remain intact. The website has its own R2 photo copies and only serves photos in its current catalogue. API tests verify safe projection, explicit selections, price updates, stale snapshot rejection and sold-car exclusion. The cross-window authenticated browser flow still needs a user trial; on an authentication interruption, sign in to both Sites and restart the sync.

Car creation requires only brand and model. Searchable grouped pickers offer curated popular shortcuts, then alphabetical choices; custom text and previously saved values remain available. Models depend on brand. Optional numeric values persist as null, dates stay blank, and missing VINs use reserved internal unique index keys without exposing fabricated VINs. Entered VINs remain unique. Contract generation separately requests missing VIN/year.

Cost basis supports KRW delivered-to-Bishkek amount, KRW per USD, TPO in USD, USD/RUB, logistics Bishkek–Voronezh in USD, and documents/recycling fee in rubles. Legacy extra expense records add to these amounts. Missing FX leaves totals explicitly incomplete, never fabricating an exchange rate. Rates are manually fixed per vehicle.

The authenticated inventory replacement endpoint validates every input, uses expected IDs/revisions as a transactional guard, retains original cards in inventory_backup_cars and their file chunks, and is idempotent by batch ID. Backups and original downloads are accessible under /api/inventory-backups. No sample or imported inventory is shipped in the client.

Separate photo and video actions: photos upload sequentially as a multi-file queue with stable upload IDs for safe retries. Video gallery uses native controls and range-aware streaming responses, including HEAD, suffix ranges and invalid-range rejection. Videos are excluded from document lists and website photo exports.

Authentication uses Sites dispatch-owned ChatGPT identity headers; only the stable site-scoped user ID determines membership. Every API route requires an active CRM membership. Viewer writes, editor access management, inventory backups/replacement, archive and website publishing are denied server-side. Owner registration requires a secret runtime bootstrap capability and can happen only once. Invitations are hashed, single-use, seven-day tokens, never emailed automatically; invite acceptance binds the authenticated user ID, not the display email. Staff still require platform-level private Site viewer access. Server-side audit events record the authenticated actor, and revocation takes effect on the next API request. Read-only UI has disabled forms and hidden write actions.

External employee access uses owner-issued personal login links, independent of ChatGPT. Raw random 244-bit link and session credentials are hashed in D1; links expire after seven days and can be redeemed once, sessions expire after 30 days. Secure HttpOnly SameSite=Lax host-only cookies carry the session, and each API request rechecks active membership and role. Logout destroys the session; revocation invalidates all employee sessions and unused links. Public authentication routes enforce same-origin JSON POST and a 4 KiB body bound. No public signup or automatic email exists. Public Site audience activation requires explicit owner approval; while Sites remains private its upstream ChatGPT sign-in still applies.
